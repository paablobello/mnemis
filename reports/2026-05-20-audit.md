# Auditoría técnica de Mnemis - 2026-05-20

## Resumen ejecutivo

Mnemis está en buen estado para una alpha técnica: el monorepo está ordenado,
los contratos principales están testeados, hay separación clara entre API,
worker, SDK/CLI/MCP, DB e indexer, y los checks base pasan. No encontré P0.

El nivel de calidad actual es suficientemente sólido para seguir iterando con
usuarios técnicos tempranos. Tras esta auditoría se remediaron los P1 de
dependencias vulnerables, límites reales de body, registro de instalaciones
GitHub App, degradación de providers externos y contrato SDK/API de búsqueda.
También se cerró el rate limiting in-memory con un backend Postgres compartido
para modo cloud/distribuido.

## Estado tras implementación

Remediado en este ciclo:

- `drizzle-orm` actualizado a `^0.45.2`, `drizzle-kit` a `^0.31.10` y
  override raíz de `esbuild` a `^0.25.12`; `bun audit` queda limpio.
- Lectura limitada por bytes para JSON/text y webhooks, incluyendo requests sin
  `Content-Length`.
- Verificación server-side opcional de GitHub App installation cuando hay
  credenciales de app, y requerimiento en `MNEMIS_MODE=cloud`.
- Fallback keyword-only/sin embedding para fallos Voyage y sin contextual prefix
  para fallos Anthropic en indexing.
- `ChunkSearchItem` del SDK alineado con la respuesta real de `/v1/search`.
- Rate limiting con backend `postgres` sobre `usage_events`, advisory lock por
  bucket y `MNEMIS_TRUST_PROXY` para aceptar headers proxy explícitamente.

## Destilación de arquitectura

- Runtime: TypeScript en monorepo Bun/Node 22 con workspaces `apps/*` y
  `packages/*`.
- API: Hono con middleware de headers seguros, body limit, API key auth,
  scopes, rate limit y rutas `/v1`.
- Persistencia: Postgres con Drizzle, `pgvector`, `tsvector`, triggers post
  migrate y constraints SQL adicionales.
- Worker: jobs en tabla Postgres, polling, cron, clonación GitHub, crawling
  docs/local, contextual prefixes, embeddings y upsert idempotente de chunks.
- Retrieval: Postgres FTS + pgvector + RRF, con rerank Voyage/local opcional y
  síntesis Anthropic opcional.
- Superficies públicas: REST API, TypeScript SDK, CLI y MCP comparten contratos
  conceptualmente, aunque no todos están generados desde una única fuente.

Fortalezas reales:

- Workspace scoping consistente en las rutas críticas de memoria, sources,
  jobs y search.
- Scopes finos para lectura/escritura, contenido, embeddings, hard delete,
  admin sweep y local sources.
- `config.localPath` está deshabilitado por defecto, requiere scope dedicado y
  allowlist de roots tanto en API como en worker.
- Webhooks GitHub validan `x-hub-signature-256` con HMAC y `timingSafeEqual`.
- Job payloads y errores operativos se redaccionan antes de salir por API.
- Tests cubren auth, scopes, local sources, webhooks, indexing, cron, search,
  SDK, CLI, MCP y calidad básica de retrieval.

## Hallazgos originales

### P1 - `drizzle-orm` tiene una vulnerabilidad alta pendiente

Evidencia:

- `bun audit` reporta `drizzle-orm <0.45.2` con GHSA-gpj5-g38j-94v9.
- Versiones actuales: `apps/api/package.json` usa `drizzle-orm ^0.36.0` y
  `packages/db/package.json` usa `drizzle-orm ^0.36.0`.

Impacto: riesgo de SQL injection por escaping incorrecto de identificadores en
Drizzle. Aunque el código usa parámetros para valores, el advisory afecta a la
dependencia base y debe cerrarse antes de alpha pública.

Recomendación: actualizar `drizzle-orm` a `>=0.45.2` y `drizzle-kit` a una
versión compatible, regenerar/validar schema, correr `db:push:ci`, lint,
typecheck, tests y audit. Revisar también el advisory moderado de `esbuild`
arrastrado por `drizzle-kit`; es de tooling/dev server, menor para runtime.

### P1 - El registro de instalaciones GitHub App es trust-on-first-claim

Evidencia:

- `apps/api/src/routes/github.ts:19-25` permite registrar una instalación con
  una API key que tenga `sources:write`.
- `apps/api/src/services/github-installations.ts:47-103` guarda
  `installationId`, `accountLogin`, permisos y eventos enviados por el cliente
  sin validarlos contra GitHub.
- `apps/api/src/services/sources.ts:223-228` solo comprueba que la instalación
  esté vinculada al workspace.
- `apps/worker/src/runner.ts:294-300` usa esa instalación para pedir token y
  clonar repos privados.

Impacto: en un entorno multi-tenant/cloud, un cliente podría reclamar un
`installationId` que no le pertenece si lo conoce antes de que lo registre su
dueño. Para self-host single-tenant es aceptable, pero no para hosted cloud ni
alpha pública con tenants no confiables.

Recomendación: reemplazar el registro manual por callback OAuth/GitHub App con
`state` firmado, o validar server-side la instalación con la GitHub App API
antes de persistirla. Al crear un source privado, validar que el repo pedido
pertenece a la instalación y que los permisos son suficientes.

### P1 - El límite de body depende de `Content-Length` y no cubre webhooks

Evidencia:

- `apps/api/src/middleware/body-limit.ts:10-26` solo rechaza si existe
  `content-length` y supera el máximo.
- `apps/api/src/app.ts:40-44` monta webhooks antes del body limit y el body
  limit solo aplica a `/v1/*`.
- `apps/api/src/routes/webhooks.ts:13` lee el raw body completo con
  `c.req.text()`.
- Rutas JSON como `apps/api/src/routes/search.ts:22-25` y
  `apps/api/src/routes/memories.ts:112-117` leen todo el body con `c.req.json()`.

Impacto: un cliente puede enviar chunked transfer sin `Content-Length` y forzar
lectura completa en memoria. Los webhooks tienen el mismo problema. Es un DoS
barato si el API queda expuesto.

Recomendación: implementar un lector limitado por bytes para JSON/text, aplicar
el mismo límite a `/v1/webhooks/github`, y testear requests sin
`Content-Length` que excedan `MNEMIS_MAX_BODY_BYTES`.

### P1 - Proveedores opcionales pueden hacer fallar flujos core en vez de degradar

Evidencia:

- `apps/worker/src/contextual-prefix.ts:291-315` hace llamadas Anthropic por
  chunk sin retry ni aislamiento por chunk; cualquier error sale hacia el job.
- `apps/worker/src/embeddings.ts:99-117` propaga errores de embeddings Voyage.
- `apps/worker/src/runner.ts:493-581` marca el source y el job como `failed`
  ante cualquier error.
- `apps/api/src/services/memories.ts:100-120` propaga errores de embedding al
  crear una memoria.

Impacto: si Anthropic o Voyage están configurados pero caídos/rate limited, el
producto puede dejar de indexar o guardar memorias, aunque podría funcionar en
modo keyword-only. Para alpha pública, los proveedores deben ser aceleradores,
no puntos únicos de fallo.

Recomendación: degradar por defecto a indexación keyword-only/memoria sin
embedding con warning en job result, y reservar `failed` para errores core
como source inaccesible o schema. Añadir retries con backoff para errores 429/5xx.

### P1 - Rate limiting era in-memory y confiaba en headers proxy

Estado: remediado.

Evidencia:

- `apps/api/src/middleware/rate-limit.ts` soporta backend `memory` y
  `postgres`; en `MNEMIS_MODE=cloud` el default es `postgres`.
- El backend Postgres usa `usage_events` con `kind='request'` y advisory lock
  transaccional por bucket/ventana.
- `MNEMIS_TRUST_PROXY=true` es necesario para usar `x-forwarded-for` o
  `x-real-ip`; sin esa opción se ignoran esos headers.
- `apps/api/tests/rate-limit-db.test.ts` valida que dos instancias Hono
  compartan el mismo bucket.

### P2 - El SDK no refleja exactamente la respuesta real de `/v1/search`

Evidencia:

- `apps/api/src/routes/search.ts:45-53` arma `items` desde `chunkToDto(...)` y
  añade `citation_number` y `permalink`.
- `apps/api/src/services/source-search.ts:354-386` devuelve `id`, `source_id`,
  `source_kind`, `source_identifier`, etc.; no devuelve `n` ni `chunk_id`.
- `packages/sdk/src/types.ts:227-254` define `ChunkSearchItem extends
  ChunkSearchCitation`, exigiendo `n` y `chunk_id` en cada item.

Impacto: consumidores TypeScript pueden escribir contra campos que el API no
devuelve. Esto reduce la confianza en el SDK justo donde debería ser la
superficie más estable.

Recomendación: corregir `ChunkSearchItem`, añadir tests de contrato API-SDK
para `/v1/search`, y considerar generar tipos desde schemas compartidos.

### P2 - Cron puede encolar duplicados con múltiples workers

Evidencia:

- `apps/worker/src/cron.ts:193-244` lista cron sources, consulta último job e
  inserta un nuevo job sin transacción/advisory lock/constraint de idempotencia.
- `apps/worker/src/runner.ts:589` llama `enqueueDueCronJobs` en cada loop antes
  de reclamar un job.
- Webhooks sí usan advisory lock en `apps/api/src/services/github-webhooks.ts`,
  lo que muestra el patrón esperado.

Impacto: con dos workers, ambos pueden ver que no hay job queued/processing y
crear reindexes duplicados para el mismo minuto. Docker prod usa un worker, así
que no es P1 para self-host simple, pero bloquea escalado horizontal limpio.

Recomendación: envolver cron enqueue en transacción con advisory lock por source
y due minute, o persistir un idempotency key único en jobs.

### P2 - Jobs fallidos no tienen retry/backoff operativo para errores transitorios

Evidencia:

- `apps/worker/src/runner.ts:145-217` requeuea solo jobs `processing` stale.
- `apps/worker/src/runner.ts:465-480` marca errores normales como `failed`.
- `JOB_MAX_ATTEMPTS` aplica a stale processing, no a fallos 429/5xx de providers.

Impacto: una interrupción breve de GitHub/Voyage/Anthropic/Firecrawl puede dejar
sources permanentemente failed hasta intervención manual.

Recomendación: clasificar errores retryable vs permanent, incrementar attempts,
programar `scheduledAt` con backoff y guardar causa sanitizada.

### P3 - Duplicación de config/env y guardrails entre API y worker

Evidencia:

- API valida local sources en `apps/api/src/services/sources.ts:111-162`.
- Worker repite lógica en `apps/worker/src/runner.ts:97-132`.
- Hay `loadEnv` separados en `apps/api/src/env.ts` y `apps/worker/src/env.ts`,
  mientras varios servicios leen `process.env` directamente.

Impacto: riesgo de drift entre aceptación API y ejecución worker. Ya hay tests,
pero la intención de seguridad vive en dos sitios.

Recomendación: extraer helpers compartidos de env parsing y path allowlist a un
paquete interno, y hacer que servicios lean env normalizado inyectable.

### P3 - Documentación de decisiones técnicas está parcialmente desactualizada

Evidencia:

- `docs/research/tech-decisions.md:34` habla de BullMQ/Redis o pg-boss, pero la
  implementación actual usa tabla `jobs` en Postgres.
- `docs/research/tech-decisions.md:90-92` conserva `voyage-3.5-large` como
  default conceptual, mientras el código usa `voyage-4-large` y el baseline lo
  documenta.
- `README.md:7-10` declara alpha, pero no lista limitaciones operativas clave.

Impacto: nuevos contribuidores pueden seguir decisiones antiguas o comparar el
repo contra un diseño que ya cambió.

Recomendación: añadir un `docs/architecture.md` que represente el estado real,
y marcar `tech-decisions.md` como historical rationale.

## Riesgo residual para alpha pública

Recomiendo resolver como mínimo antes de usuarios externos no confiables:

1. Upgrade de Drizzle y audit limpio o con excepciones justificadas.
2. Body limit real para JSON/text/webhooks.
3. Registro GitHub App validado server-side o marcado explícitamente solo
   self-host/trusted.
4. Degradación de provider failures en indexación y memory save.
5. SDK contract fix para `/v1/search`.

Con esos cambios, el proyecto quedaría en una base fuerte para una alpha pública
de desarrolladores técnicos.

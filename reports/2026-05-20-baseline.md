## Results

`keyword` runs only Postgres BM25; `hybrid` adds Voyage vector retrieval and
fuses with RRF (k=60). Each row is the same retrieval policy followed by the
listed reranker.

| variant   | reranker                              | nDCG@10 | MRR@10 | Recall@5 |
| --------- | ------------------------------------- | ------- | ------ | -------- |
| keyword   | —                                     | 0.193   | 0.229  | 0.192    |
| keyword   | `Xenova/bge-reranker-base` (ONNX q8)  | 0.414   | 0.492  | 0.317    |
| keyword   | Voyage `rerank-2.5`                   | **0.502** | **0.575** | **0.567** |
| hybrid    | —                                     | 0.057   | 0.164  | 0.108    |
| hybrid    | `Xenova/bge-reranker-base` (ONNX q8)  | 0.361   | 0.494  | 0.317    |
| hybrid    | Voyage `rerank-2.5`                   | 0.441   | 0.525  | 0.467    |

## Reading the numbers

- **Voyage rerank is the clear win**: on top of plain keyword retrieval it
  jumps from 0.193 → 0.502 nDCG@10 (+160 %) and almost triples Recall@5
  (0.192 → 0.567). On hybrid it lifts retrieval from 0.057 → 0.441.
- **Local BGE rerank is the strong free option**: keyword + local more than
  doubles nDCG@10 and MRR@10 versus no-rerank, with a smaller Recall@5
  bump. The model runs locally via `@huggingface/transformers` (q8 ONNX,
  ~120 MB on disk) so it's the default when `VOYAGE_API_KEY` is absent or
  egress is restricted.
- **Hybrid alone (no rerank) underperforms keyword**: this dataset is full of
  highly lexical queries ("where is the GitHub push webhook handled",
  "what reranker options"). Voyage embeddings retrieve semantically-close
  but off-topic chunks that the RRF fusion never demotes. A cross-encoder
  fixes the ordering and brings hybrid back above keyword alone in MRR
  and Recall.
- The first request through the local reranker spent ~25 s downloading the
  model. Subsequent reranks complete in 150-500 ms for ten documents.
- Voyage `rerank-2.5` adds ~150-300 ms per query on top of the SQL fan-out.

## How to reproduce

```bash
# 1. Fresh DB schema + bootstrap a benchmark workspace
bun run docker:up
bun run db:push:ci
bun run db:bootstrap -- --email bench@mnemis.test --workspace mnemis-benchmark
# (save the printed mn_… key as MNEMIS_API_KEY)

# 2. Start worker + api allowing local sources
export MNEMIS_ALLOW_LOCAL_SOURCES=true
export MNEMIS_LOCAL_SOURCE_ROOTS=$(pwd)
bun run worker:dev &

# 3. Index once
bun run api:dev &
export MNEMIS_API_URL=http://localhost:8787 MNEMIS_API_KEY=mn_…
bun run benchmark > reports/raw/baseline-hybrid.txt
SOURCE_ID=<id printed above>

# 4. Swap reranker provider per run (kill+restart the API, keep worker)
MNEMIS_RERANK_PROVIDER=voyage bun run api:dev &
MNEMIS_BENCHMARK_SOURCE_ID=$SOURCE_ID bun run benchmark > reports/raw/baseline-voyage.txt

MNEMIS_RERANK_PROVIDER=local bun run api:dev &
MNEMIS_BENCHMARK_SOURCE_ID=$SOURCE_ID bun run benchmark > reports/raw/baseline-local.txt
```

## Caveats

- 10 queries is enough to expose a trend (no rerank ≪ local rerank < Voyage
  rerank) but too few for a published quality claim. Extend
  `packages/eval/data/mnemis-self/queries.json` before quoting these
  numbers externally.
- The corpus is the Mnemis repo itself, so vocabulary is unusually
  specific. BEIR or MTEB subsets would give a less biased view.
- Voyage rate limits: free accounts allow only 3 RPM / 10 K TPM, which
  blocks the indexing job entirely. A paid Voyage plan is required to
  reproduce the rerank rows.
- `Xenova/bge-reranker-v2-m3` is currently gated on Hugging Face
  (`Unauthorized access to file`). Default switched to
  `Xenova/bge-reranker-base`; override with `MNEMIS_LOCAL_RERANK_MODEL`
  when the v2-m3 repository opens up again.
- Voyage's embeddings API caps each batch at 120 K tokens. We lowered
  `MAX_BATCH` from 128 to 64 in `packages/embeddings/src/index.ts` to
  stay comfortably under the cap with contextual prefixes attached.
